# 用户、资产、账号与授权

[返回 README](../README.md)

## 三种身份

| 对象 | 示例 | 负责什么 |
|---|---|---|
| JumpServer 个人用户 | `operator-example` | 平台登录身份、授权对象、会话审计中的操作人 |
| 设备 Linux 用户 | `developer` | 设备上的文件、sudo、Docker 和桌面权限 |
| 资产账号记录 | 资产关联的 `developer` | JumpServer 连接设备时使用的系统凭据 |

平台用户密码与设备系统密码相互独立，不能互相替代。团队成员使用个人平台账号；不要共享管理员账号。授权普通用户连接系统账号，不等于授权查看或导出其密码。

## 创建两个资产

同一机器人分别创建终端和桌面资产，平台复用现有 `Linux` 与经过验证的 `Ubuntu-RDP`，避免反复新增平台。

| 字段 | 终端资产 | 桌面资产 |
|---|---|---|
| 名称 | `edge-01` | `edge-01-desktop` |
| IP / 主机 | 实际设备 Tailscale IPv4 | 同一地址 |
| 平台 | Linux | Ubuntu-RDP |
| 协议 / 端口 | SSH / 22 | RDP / 3389 |
| 节点 | 团队或设备类型节点 | 与终端资产一致 |
| 激活 | 开启 | 开启 |
| 资产账号 | 现有 Linux 开发账号 | 同一开发账号或经批准的专用账号 |

在受控网页中录入系统凭据，不放在 Markdown、命令行、CSV 示例或截图中。桌面使用原开发账号时，已有项目目录和环境可复用；共享账号可能有并发 GNOME 会话冲突，不提供多人独立桌面隔离。

## 个人用户与用户组

管理员创建个人用户，设置适合组织的首次登录、密码更新、到期时间和认证方式；加入如“运维人员”的明确用户组。批量导入应从当前部署页面下载模板，先核对必填字段、唯一用户名/邮箱以及已存在用户，再在受控位置生成真实表格。仓库不提供真实用户表，即使原文件名包含 NO-CREDENTIALS 也不提交。

## 授权规则

1. 每个团队/设备类别建立清晰规则，选择个人用户或用户组。
2. 指定资产或节点、允许使用的资产账号、SSH/RDP 协议及授权有效期。
3. 节点授权会覆盖日后加入节点的资产，先确认这正是管理意图。
4. 检查并收窄不必要的整个 DEFAULT 节点授权，避免“为了方便”保留全量访问。
5. 使用普通个人用户重新登录或刷新授权，确认只出现被授权资产。不要以管理员全量资产视图代替权限验证。

## 后续人工验收

按个人账号分别检查资产可见性、SSH 与 RDP 登录、实际 Linux 身份和开发目录；再检查审计中的平台操作人、目标资产、系统账号和回放。连接性自动化任务依赖 Ansible executor，其失败不能单独证明 Web SSH 不可用。
