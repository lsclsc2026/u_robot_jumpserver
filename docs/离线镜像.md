## 下载与导入

以下命令供未来在有权限的镜像准备主机执行，本次没有联网拉取或操作 Docker。按固定摘要拉取，然后恢复脚本期待的标签；`latest` 只是历史标签，不允许据此假定新下载内容相同。

```bash
# 示例：拉取固定 linux/amd64 Core 镜像。
docker pull --platform linux/amd64 jumpserver/core@sha256:99b2fd9100b0434ba4c30ff135c2b41387776a141f06d0c6bb39dc0d9b6321cc
docker tag jumpserver/core@sha256:99b2fd9100b0434ba4c30ff135c2b41387776a141f06d0c6bb39dc0d9b6321cc jumpserver/core:v4.10.19-ce
```

其余镜像按上表替换仓库名、摘要和标签。需要离线介质时，在准备主机通过 `docker save -o <文件.tar> <镜像:标签>` 导出，再用 `sha256sum <文件.tar>` 生成本次导出清单；在部署主机先校验再 `docker load -i <文件.tar>`，检查平台、标签和镜像内容。

如使用原 tar 副本，在文件所在目录校验：

```bash
sha256sum -c /path/to/repository/offline/archives.sha256
# 校验通过后，导入所需文件，示例：
docker load -i jumpserver_core_v4.10.19-ce.tar
```

重新 `docker save`/`crane pull` 得到的 tar 可以有不同元数据/打包顺序，因此即使镜像内容相同，tar SHA-256 也可能不同。原服务器脚本严格要求归档哈希；不能用新 tar 覆盖旧清单后假称精确恢复，需审阅镜像 config/rootfs 与新归档来源，再独立记录迁移修改。

## 历史下载脚本依赖

`download-images.py` 依赖脚本同目录的 `bin/crane` 与已存在的 `images/`，会根据标签查询摘要并写入初始五镜像清单；现在不应直接用它重新确定本次固定版本，使用上表摘要。

`download-lion.py` 固定 Lion 摘要并从 registry blobs 构建 tar。`finish-executor-download.py` 是恢复部分 Ansible 下载的历史工具，需要 `ansible-registry-manifest.json`、`ansible-image.json`、原部分 tar 与 `bin/crane`，不是从零开始的通用下载命令。元数据在仓库 `offline/metadata/`，需要时在 Git 外的工作区按代码相对路径布置。

本仓库不分发原 `crane` 二进制；可从其上游 go-containerregistry 项目取得与准备主机架构匹配的工具，核对其发行物校验与许可。原离线二进制和所有归档仍在本机交接包。

## 初始五镜像与后补镜像

[offline/images/manifest.json](../offline/images/manifest.json) 保留原五镜像格式，历史初装脚本明确要求 `len(images) == 5`，不能用七项清单覆盖。新增 [image-inventory.json](../offline/image-inventory.json) 才是完整七镜像清单；Lion/Ansible 和原始 registry manifest 在 [metadata](../offline/metadata)。

`ansible-image-parallel.json` 是历史并行重建过程的元数据，不是第八个交付镜像；实际交付以七项完整清单和已检查的文件为准。
